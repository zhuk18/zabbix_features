# Use case'ы топологии и их поддержка тэговой моделью

Дополнение к `topology-tags-vs-model-debate.md` и
`topology-tags-desync-tradeoffs.md`. Оба документа сравнивали граф-модель
(`topo_nodes`/`topo_edges`, см. `topology-prototype-spec.md`) с наивным
вариантом тэгов: host-тэги, которые пишет внешний скрипт (как в
`zabbix-AutoMapper`). Этот вариант проигрывает почти везде, и это уже
зафиксировано.

Здесь каждый use case сравнивается с самым сильным тэговым вариантом,
какой удалось собрать (далее T-модель). Он закрывает заметно больше, чем
признавали предыдущие разборы, и сдвигает сам вопрос спора (см. «Вывод»).

## 1. T-модель

```
# Слой 1. Наблюдения: LLD на репортере по lldpRemTable, по одному item на соседа
item prototype: lldp.rem[{#LOCPORT},{#REMIDX}]   # значение = сырая запись соседа, пишется в историю
  tags: interface={#IFNAME}          # тот же тэг, что в стандартных сетевых шаблонах
        topo.peer.id={#REM.CHASSIS}  # sysname, если chassis нет
        topo.peer.port={#REM.PORTID}
        topo.via=lldp|cdp
# свой chassis репортера хранится как значение item'а lldp.loc.chassis, а не как тэг

# Слой 2. Идентичность и ручные решения: host-тэги
topo.id=<chassis_id>                          # тэг многозначный, значений может быть несколько
topo.link.manual=<local_port>><peer.id>:<peer_port>
topo.link.suppress=<local_port>

# Слой 3. Сборка графа при чтении
item.get(tags topo.*, selectItemDiscovery) + host.get(tags, inventory) → граф в памяти
```

Ключевое отличие от граф-модели: собранный граф нигде не хранится,
reconciliation (правила §3 спеки: трёхключевая склейка, merge сторон
линка, приоритет manual) выполняется при каждом чтении.

FR уже говорит, что репортер «stores topology observations in
topology-related items». Слой 1 почти совпадает с тем, что заложено в
FR. Модели расходятся только в одном: хранится ли собранный граф или
вычисляется на лету.

Отвергнутый подвариант: немониторимых соседей можно было бы создавать
как хосты через LLD host prototypes. Он ломается на A2 (см. ниже):
второй репортер не создаст хост с тем же именем, а жизнь такого хоста
привязана к LLD-правилу первого репортера.

Легенда вердиктов:

- ✅ закрывается штатными механизмами Zabbix;
- 🟡 закрывается ценой самописной логики или ограничений;
- 🔴 без хранимого состояния по-настоящему не закрывается.

## 2. Use case'ы

### A. Обнаружение и идентичность

| # | Use case | Как в T-модели | Вердикт |
|---|---|---|---|
| A1 | Найти устройства, которые Zabbix не мониторит (FR 1a) | Reader берёт все `topo.peer.id`, не совпавшие ни с одним `topo.id` или inventory MAC хоста | ✅ для самого обнаружения. Но устройство здесь только строка. Подписать его, закрепить на схеме, пометить «игнорировать» нельзя без placeholder-хоста → в целом 🟡 |
| A2 | Один сосед виден двум репортерам (FR 4c) | Reader группирует по `peer.id` | ✅, если оба репортера видят одинаковый идентификатор. Если один видит chassis, а другой только sysname, трёхключевая склейка повторяется на каждом рендере и не помнит прошлых совпадений → 🟡 |
| A3 | Сменился chassis_id (замена платы, сброс) | Склейка по mgmt_ip сработает, только если он есть в той же выборке | 🔴. Ручные решения, привязанные к старому id (`topo.id` на хосте, `topo.link.manual`), молча отваливаются. Граф-модель помнит сущность и переписывает ключ (§3 rule 4) |
| A4 | Сосед становится репортером | Его item со своим chassis совпадает со строками у других репортеров, и склейка происходит автоматически | ✅, честный плюс. Класс багов, найденных на лабе (дубли Device, двухпроходный merge unconfirmed-портов), в read-time модели не возникает в принципе, потому что нечему дублироваться |
| A5 | Device ↔ Host (MAC, reporter_self, manual) | MAC сравнивается с inventory, репортер сопоставляется сам с собой, manual делается через тэг `topo.id` на хосте | ✅ по механике. Но 1:1 ничем не защищено: у двух хостов может оказаться один `topo.id` (например, после Clone host). Reader должен находить и показывать такой конфликт → 🟡 |
| A6 | Device ↔ Proxy | У объекта proxy нет тэгов | 🔴 напрямую. Обходной путь — через Host машины, на которой работает proxy, или через конвенцию на стороне хоста |
| A7 | Стек, MLAG, BMC+OS | Многозначный `topo.id`: один хост соответствует N chassis | ✅, и здесь тэги гибче граф-модели, где 1:1 остаётся главным известным ограничением. Обратная сторона: случай «два хоста на один chassis» (BMC+OS) reader должен отличать от ошибки из A5, иначе правила валидности противоречат друг другу |

### B. Связи

| # | Use case | Как в T-модели | Вердикт |
|---|---|---|---|
| B1 | Линк порт-порт, drill-down по портам | Пары item-тэгов, порт определяется тэгом `interface`. Порты без соседей видны по interface-items стандартного шаблона | ✅ |
| B2 | Две стороны одного линка сливаются в один (FR 4e) | Reader сопоставляет `(self.id, port)` с `(peer.id, peer.port)`. Канонизация не нужна, потому что ничего не записывается | ✅. Нормализация `peer.port` (разные `lldpRemPortIdSubtype`) всё равно нужна, просто на чтении, а не в ingest |
| B3 | Per-side staleness (FR 5a/5b) | У каждой стороны свой LLD-item. Если сторона замолчала, её item становится lost resource, а `lastcheck` работает как last_seen этой стороны. «Stale до ручного удаления» настраивается через Delete lost resources = Never | ✅ нативно. В desync-tradeoffs этот кейс оценён хуже, потому что там рассматривались host-тэги, а не LLD |
| B4 | Ручной линк, discovered не перекрывает manual (FR 4f) | Host-тэг `topo.link.manual` плюс правило приоритета в reader | ✅, если оба конца — хосты. Если один конец — устройство без хоста, привязка держится только на строке. Для пассивного железа (patch panel) нужен placeholder-хост. Проверки при записи (порт уже занят, опечатка в id) нет, ошибки видны только при чтении → 🟡 |
| B5 | Вручную удалённый discovered-линк возвращается (FR 5c) | LLD создаст item заново. Для постоянного подавления есть `topo.link.suppress` | ✅ (зависит от того, можно ли удалить discovered item вручную, см. §4) |
| B6 | LAG | LLD по `ieee8023adTable`, тэг `topo.lag` на item порта | ✅ на уровне модели. Коллектора нет ни в одной из моделей |
| B7 | Окраска линка по триггерам | Триггеры на interface-items наследуют тэг `interface` | ✅, даже проще, чем через `zabbix_itemids` |
| B8 | «Что было подключено к порту 24 неделю назад» | История значений neighbor-item | ✅. Бонус, которого в граф-модели нет: там только last_seen, temporal versioning вне scope |

### C. Эксплуатация

| # | Use case | Как в T-модели | Вердикт |
|---|---|---|---|
| C1 | «Что за этим свитчем», blast radius | Собрать весь граф из тэгов всех репортеров и обойти его | 🟡. Работает, но каждый запрос требует полной сборки. На тысячах репортеров появится кэш с инвалидацией, а это по сути и есть topo-таблицы. Сами алгоритмы вне MVP в обеих моделях |
| C2 | Proxy blind spot | Live `host.get`, как и в граф-модели | ✅, одинаково в обеих моделях |
| C3 | Подавление каскадных алертов | Штатный механизм Zabbix — trigger dependencies. Ни одна модель не делает этого сама, обе могут служить источником для генератора зависимостей | Паритет |
| C4 | Actions и фильтры «по топологии» | Event tags наследуют host tags | ✅ для атрибутных условий (сайт, роль). Реляционные условия («соседи упавшего свитча») без доработки actions не делает ни одна модель. Частичный плюс тэгов |
| C5 | Service → Host | В Zabbix это уже работает на тэгах (problem tags сервиса) | ✅. Следствие: Service лучше убрать из topo-модели совсем, а не держать в бэклоге |
| C6 | VM → гипервизор | Макросы гипервизора в VMware host prototypes, тэг `topo.hosted_by` в прототипе | ✅ (конкретные макросы нужно проверить) |

### D. Платформа

| # | Use case | Как в T-модели | Вердикт |
|---|---|---|---|
| D1 | Права доступа | Тэг на видимом хосте раскрывает идентификатор соседа, к которому у пользователя нет доступа. Любой, у кого есть write на хост, может поменять `topo.*`, например случайно при правке тэгов для алертинга | 🔴/🟡. В граф-модели отдельные права тоже требуют работы, но их есть где задать |
| D2 | Export/import, backup, миграции | Ручные решения в host-тэгах переезжают вместе с конфигом, LLD-объекты пересоздаются сами | ✅, сильный плюс тэгов. Минус: Clone host копирует `topo.id` |
| D3 | Массовые запросы («все протухшие линки», «все немониторимые») | Один `item.get` по тэгам с `selectItemDiscovery`, склейка в PHP | ✅ на сотнях устройств. На десятках тысяч портов нужен кэш (см. C1) → 🟡 |
| D4 | Позиции узлов, заметки, ручные атрибуты для немониторимых устройств | Хранить негде, потому что нет Zabbix-объекта | 🔴. В граф-модели это тоже бэклог, но место для хранения есть |
| D5 | L3 (роадмап 8.2) | OSPF/BGP-соседи по той же LLD-схеме, принадлежность к подсети выводится из host interfaces на чтении | Примерный паритет |
| D6 | Пассивная инфраструктура | Placeholder-хост. В граф-модели это manual Device, тоже бэклог | 🟡 в обеих |
| D7 | Нагрузка | Один LLD-item на каждого соседа на каждом репортере. LLDP-MED телефоны на access-свитчах дают соседа почти на каждом порту, так что на крупной инсталляции это десятки тысяч items. В граф-модели — одна blob-item на репортер | 🟡, это цена T-модели |
| D8 | Недоверенные LLDP-строки (§9 спеки) | Значения тэгов стандартный frontend экранирует, но собственный UI графа всё равно должен экранировать сам. Тэг ограничен 255 символами | Паритет |

## 3. Вывод

Сильный вариант T-модели закрывает почти весь MVP-scope FR: 1a/1b,
4c/4e/4f, 5a–c. В нескольких местах он лучше граф-модели:

- per-side staleness и merge двух сторон получаются из LLD бесплатно;
- баги reconciliation не возникают конструктивно;
- стеки и MLAG представимы;
- история подключений есть из коробки;
- export/import работает сам.

Тезис «тэги не тянут FR» в форме из `topology-tags-vs-model-debate.md` и
`topology-tags-desync-tradeoffs.md` после этого разбора не держится. Он
верен для host-тэгов, которые пишет скрипт, но не для LLD-items с
item-тэгами.

Настоящий водораздел проходит не между тэгами и таблицами, а между
stateless и stateful. T-модель ломается ровно там, где нужна память о
вещах, у которых нет владельца в Zabbix:

- континуитет идентичности при смене ключей (A3);
- ручные решения и атрибуты для немониторимых и пассивных устройств
  (B4, D4, D6);
- гарантии при записи вместо обнаружения ошибок при чтении (A5, D1);
- масштаб, при котором read-time сборке понадобится материализованный
  кэш (C1, D3).

Вопрос для решения: какие из этих stateful-кейсов реально входят в 8.2?

- Если в scope только то, что сейчас записано в FR, T-модель достаточна
  и заметно дешевле.
- Как только в scope попадают ручная работа с немониторимыми
  устройствами или большие инсталляции, таблицы понадобятся.

Компромисс, который стоит обсудить: наблюдения хранятся в items (как FR
и так предполагает), а `topo_nodes`/`topo_edges` сводятся к двум ролям:
хранилищу того, чего нет в Zabbix (unmanaged Device, manual links,
overrides), и кэшу сборки.

## 4. Что проверить до обсуждения

Эти факты не подтверждены для 8.x, а от них зависят вердикты:

- можно ли вручную удалить отдельный discovered item (B5, FR 5b/5c);
- какие поля `selectItemDiscovery` отдаёт в текущей версии (`lastcheck`,
  статус lost resource) (B3);
- действительно ли у объекта proxy по-прежнему нет тэгов (A6);
- как ведёт себя LLD host prototype при конфликте имени с хостом из
  другого LLD-правила (подвариант в §1, A2);
- какие макросы гипервизора есть в VMware LLD (C6).
